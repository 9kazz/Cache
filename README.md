# Cache

Стратегии кэширования (LRU, LFU, ARC, 2Q, LIRS), многоуровневая иерархия кэшей
и бенчмарк для их сравнения.

## Структура

| Путь | Что там |
|---|---|
| `caches/` | Стратегии (`*_cache.hpp`), базовый класс `cache.hpp`, иерархия и `make_cache` в `cache_hierarchy.hpp`, CLI `main.cc` |
| `benchmark/` | Бенчмарк: чтение JSON (`environment.hpp`), хранилище (`data_base.hpp`), workload и оптимум Белади (`workload.hpp`, `optimal.hpp`) |
| `data/` | Датасеты для бенчмарка и генератор `generate.py` |

## Сборка и запуск

Нужен компилятор с C++20 (designated initializers, `std::in_range`, `<span>`).
MinGW 4.8.1 из CodeBlocks не подходит; проверено на g++ 13 в WSL.

CLI стратегий (`caches/main.cc`):

```bash
g++ -std=c++20 -Wall -Wextra -O2 caches/main.cc -o cache.out
echo "4 12 1 2 3 4 1 2 5 1 2 3 4 5" | ./cache.out all
echo "0 12 1 2 3 4 1 2 5 1 2 3 4 5" | ./cache.out hier lru:2 arc:4 2q:8
```

Бенчмарк (`benchmark/main.cc`) читает один датасет за запуск:

```bash
g++ -std=c++20 -Wall -Wextra -O2 benchmark/main.cc -o bench.out
./bench.out -c "path to comfig file" -d "path to data file"
```

Для сборки и запуска тестов можно использовать скрипт bench.py:

Сборка:
```bash
python3 bench.py build
```
Запуск тестов
```bash
python3 bench.py run -c "path to config file" -l "path to log file" -d "path to benchmark data directory"
```


Расширение `.out` уже есть в `.gitignore`.

Аргументы командной строки для запуска бенчмарка:
-d, --data:   путь к .json файлу с данными для тестирования
-c, --config: путь к  .json файл конфигурации архитектуры кеша

## Создание кэшей

У всех стратегий конструктор `(capacity, storage, next = nullptr)`: последний
уровень читает из медленного хранилища `storage`, остальные получают
`storage = nullptr` и уровень ниже в `next`.

По имени стратегию создаёт `make_cache`:

```cpp
make_cache<T, KeyT>(name, size, storage, next = nullptr);
```

Регистр имени не важен, `2q` и `qq` означают одно и то же, поэтому подходят и
имена CLI (`lru`, `2q`), и имена из `benchmark/config.json` (`LRU`, `QQ`).
`cache_hierarchy` создаёт уровни через неё же.

Минимальные размеры: 2Q с размером по умолчанию требует хотя бы 4 страницы,
LIRS — хотя бы 100. Для меньших размеров есть полные конструкторы.

## Датасеты (`data/`)

Формат тот же, что у `benchmark/bench_data.json`: массивы `pages`
(`{"key": int, "content": string}`) и `workload` (ключи запросов). У каждого
ключа из workload есть страница. Дополнительные поля `description`, `params` и
`stats` описывают датасет; `environment` их игнорирует.

Перегенерировать (seed'ы фиксированные, файлы совпадают побайтово):

```bash
python3 data/generate.py
```

## Последние изменения (ветка `cache_system`)

- **ARC: исправлен баг безопасности исключений.** Раньше ARC сначала освобождал
  место (`replace` / `make_room`, удаление «призрака»), а потом звал
  `slow_get_page()`. Если хранилище бросало исключение, страница была уже
  вытеснена, а новую вставить было нечем. В 84% таких случаев кэш и через 5000
  запросов оставался на cap − 1 и тихо портил статистику. Теперь страница
  загружается первой, как в LRU, LFU, 2Q и LIRS.
- **`make_cache`**: порядок аргументов как у конструкторов, имена без учёта
  регистра, `qq` — синоним `2q`.
- **`data/`**: 18 датасетов и генератор, см. выше.
- Мелочи: в 2Q три одинаковых псевдонима итератора заменены одним
  `queue_iter_t`; в LIRS и 2Q удалены неиспользуемые типы и исправлены
  опечатки; `caches/main.cc` больше не падает через `std::terminate` на
  огромном `n`.

Все 5 стратегий сверены с эталонными реализациями по статьям: 3900 случайных
прогонов с ASan + UBSan + `_GLIBCXX_DEBUG`, расхождений нет.

## Что стоит доделать в `benchmark/`

- **Собирать иерархию из `config.json`.** Сейчас `main.cc` гоняет один
  `lirs_cache(100)`, а иерархию из конфига только печатает. Собрать её можно
  так (`environment::cache_name()` для этого надо сделать public):

  ```cpp
  std::vector<std::pair<std::string, size_t>> levels;
  for (const auto& l : input.hierarchy())
      levels.emplace_back(env_t::cache_name(l.type), l.size);   // "LRU", "QQ", ...
  caches::cache_hierarchy<std::string, int> h(levels, slow_get_page);
  // h.level(i).hits() / misses() — статистика уровня i
  // h.level(h.levels() - 1).misses() — чтения медленного хранилища
  ```

- **Проверять результат `setup()`.** При ошибке (например, `-d data` — это
  папка) программа печатает ошибку, прогоняет пустой workload и возвращает 0.
- **Убрать `explicit` у конструкторов перемещения** в `workload` и
  `data_base`: `workload w = std::move(x);` молча копирует, а для `data_base`
  такая запись не компилируется.
- **Проверять, что у каждого ключа из workload есть страница** в
  `environment::get_data`, иначе `.at()` бросит исключение посреди прогона.
- **Выводить оптимум Белади** рядом с результатом: `workload::optimal_hits(cap)`
  уже есть и протестирован. Для иерархии верхняя граница — оптимум при
  суммарном размере уровней.
- Мелочь: `-Wsign-compare` в `benchmark/main.cc:30`.
